# Выпуск и восстановление

Последовательность выпуска клиента закреплена в `.github/workflows/pages.yml`. Успешное завершение общих проверок для того же SHA открывает сборку и публикацию Pages. Ручной запуск публикации работает для `main`. Проверки PR используют тот же workflow. Браузерный smoke-тест использует Playwright и команду `npm run e2e`. Полный маршрут ранней версии оставлен под `e2e:legacy` как историческая проверка.

## Пустая база

Используй отдельный пустой проект Supabase. Примени SQL в явном порядке из [supabase/fresh-install.json](../supabase/fresh-install.json). Список включает актуальную базовую схему и дополнения. Миграции ранних версий, уже перекрытые этой схемой, пропущены. CLI-сортировку файлов сюда подставлять нельзя: миграции имеют совпадающие даты, а установка ролей зависит от базового чата.

`npm run test:db:install` проверяет этот порядок, совпадение SQL с JS-правилами, наличие административных функций и права на боевые RPC в PGlite. `tools/sql/auth-stub.sql` используется только в тестах. Реальный Supabase предоставляет собственные auth и роли.

## Существующая база

1. Зафиксируй SHA клиента, версии Edge `account` и `combat`, историю реально применённых миграций и текущие правила. Проверь публичные функции `player_action` и `combat_apply`, их связи с `game_admin.core_*` и права ролей.
2. Создай резервную копию и проверь восстановление в отдельной среде. Подготовь обезличенные сценарии старого прогресса: гость, кошелёк, полная сумка, исследование и активный бой.
3. Определи список новых миграций для установленной версии и проверь его на копии. Полный `schema.sql` применяется только при установке с нуля. Повторное применение поверх админки способно заменить её обёртки обычными RPC.
4. Проверь данные до и после обновления, доступность RPC, права ролей и правила начислений. Если миграция объявлена повторяемой, примени её повторно на копии.
5. Выпусти совместимый SQL и Edge перед клиентом, когда это требуется контрактом. Проверь старый клиент и новую сборку на тестовом аккаунте. Затем проверь опубликованный SHA.

`test:db:install` восстанавливает резервную копию тестовой PGlite-базы и повторяет последние три шага установочного набора, проверяя сохранность профиля, инвентаря, кошелька, журналов и активного контекста боя. Тест подтверждает локальный сценарий. Рабочая схема Supabase и восстанавливаемость её резервных копий требуют проверки в отдельном проекте. Дополнительный `npm run test:db` запускай только на одноразовом PostgreSQL.

## Карточка выпуска

Запиши SHA клиента, версию клиента, версии боевого баланса и дуэли, хеши Edge, имена и хеши применённых миграций, ссылку на запуск проверок и результат проверки на тестовом аккаунте. Добавь дату резервной копии, объём данных после неё, ответственного и способ возврата.

При сбое клиента можно вернуть проверенную сборку, если сервер совместим с ней. При сбое SQL сначала оцени корректирующую миграцию. Возврат базы из копии требует сверки данных, появившихся после резервного копирования.

## Выпуск восстановления итогов боя

На тестовом Supabase сначала сверь установленные ревизии и административную обёртку `public.combat_apply`. Примени отдельно `202611150001_combat_receipts.sql`, затем обнови Edge `combat` из сгенерированного файла в репозитории. Проверь старый клиент и новую сборку на тестовом аккаунте, включая реальный повтор запроса. Только после проверки SQL и Edge можно публиковать клиент с новым протоколом.

Если `pg_cron` уже включён, миграция регистрирует ежедневную задачу `combat-receipts-cleanup`. Перед выпуском проверь, что задача видна и выполняется. Для среды без Cron настрой ежедневный вызов `public.combat_receipts_cleanup()` от служебной роли. Сервер перестаёт возвращать записи ровно по истечении семи суток независимо от расписания физической очистки.
