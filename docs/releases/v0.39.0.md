# Колдовство v0.39.0 — единый выпуск ребаланса

Статус: подготовлен; обновление production SQL/Edge и публикация Pages ещё не подтверждены. Ветка `codex/rebalance`, база production-кода `b7d70ac2252b7d6270b1a191c8abd6f82662dc52`. Версия клиента 0.39.0, общие правила нового боя 40, протокол новой Дуэли 3. Эти номера относятся к разным уровням и не должны заменять друг друга.

## Изменения для игрока

- Фиксированные восстановительные и тактические зелья, общий лимит категории и перезарядка; четыре быстрых типа фиксируются до боя. Антиожоговый настой снимает горение и защищает от него. Изготовление каждого зелья — строго по одному, плата за регенерационные зелья 25/30 монет.
- Десять амулетов с улучшениями +0…+5, включая Грозовое сердце. Развитие даров IV/V и полноценная Гроза I–V.
- Двенадцать городских точек сбора, повторяемые компоненты охраняемых запасов и серверная случайная добыча сапфиров с защитой от повторной выплаты.
- Асинхронная Дуэль против ИИ воспроизводит реальные надетые дары защитника, уровни, ветки, амулеты и заряды Грозы. Для новых Дуэлей уменьшен входящий урон, даны одинаковые окна применения даров и временная защита от повторного прерывания. Подбор, рейтинг, попытки и награды сохранены; случайные PvE-сапфиры в Дуэль не добавлены.
- Аналитика экономики и путей пяти школ сохранена отдельно. Она не снижает цены и не является гарантией срока прокачки каждого игрока.

## Порядок выпуска

**GitHub Pages автоматически публикует клиент при изменении `main`. Сначала обновляется сервер.** Подключение GitHub не даёт доступа администратора Supabase. Нужен доступ именно к Supabase-проекту, который указан в `VITE_SUPABASE_URL` production-сборки. Перед записью подтвердить идентификатор проекта по рабочему клиенту/настройкам Pages; не выбирать проект только по похожему названию.

1. Проверить текущий сервер и исходную схему, доступность штатного восстановления/резервной копии, отсутствие чужого параллельного выпуска. Отдельная тестовая база и короткая проверка интерфейса предпочтительны до production; уже выполненные PGlite/логические проверки не выдаются за эти проверки.
2. Опубликовать **Edge Function `combat`** из `supabase/functions/combat/index.ts`. Не менять имя функции, действующую политику JWT и существующие переменные Supabase. Это самостоятельный сгенерированный файл; `SUPABASE_SERVICE_ROLE_KEY` остаётся только на сервере.
3. Выполнить целиком **только новую миграцию** `supabase/migrations/20261021_rebalance_recovery.sql`. Она транзакционная и повторяемая; обновляет правила, поддержку Грозы, таблицу квитанций, каталог предметов поддержки и функции, сохраняя административные обёртки. Для этого обновления существующей базы не переустанавливать `schema.sql`, не запускать все старые миграции по очереди.
4. Проверить результат SQL и развёрнутую версию `combat`. Убедиться, что административные обёртки остаются на месте, а новая таблица квитанций закрыта RLS и правами. Проверить продолжение старого боя на тестовом аккаунте, не выдавая повторную награду.
5. Слить подготовленный PR в `main`, дождаться успешного `Deploy to GitHub Pages` для SHA слияния. Нельзя считать клиент опубликованным только по факту слияния.
6. Открыть опубликованную игру на ПК и мобильном размере: загрузка/вход, сумка и котёл, дары и амулеты, четыре типа зелий, новая Дуэль и её результат. На тестовом аккаунте проверить сохранение после перезагрузки и однократность награды. Зафиксировать SHA Pages и версию Edge; итоговый статус выпуска обновлять только по проверенным результатам.

Совместимость уже начатых боёв сохраняется: их проверка идёт по версии, записанной при старте. **Новые Дуэли сервер начинает только по протоколу 3** (бой 40): запрос с другой или отсутствующей версией отклоняется с причиной `update_required` до списания попытки, а старая вкладка получает сообщение «Обновите страницу». Версию дуэли больше не выбирает клиент. Обычные бои по поддерживаемым старым версиям пока допускаются. Действующие вкладки могут обновить клиент после завершения боя.

На исходной подготовленной ветке пройдены полный `npm test` и 88 проверок экономики. Для релизной версии отдельно пройдены `npm run test:chat` (включая 100 проверок политики ролей), `npm run test:admin` (31 SQL-проверка), `npm run build` и `npm run check:bundle`; полный набор повторно запускается при подготовке и в CI PR. Сгенерированные Edge, SQL-миграция и административная конфигурация соответствуют исходникам. Проверки текущих серверных прав/функций на отдельном PostgreSQL и короткая визуальная проверка опубликованного клиента ещё не подтверждены. Длительные браузерные циклы не требуются.

## При неудачном выпуске

Ошибка внутри SQL-транзакции откатывает миграцию; до исправления клиент не публиковать. Обновлённую совместимую Edge Function можно оставить для старого клиента. Если ошибка проявилась после Pages, сначала вернуть клиент на предыдущую рабочую версию и разбирать сервер отдельно. Не удалять квитанции/предметы и не возвращать старую схему поверх новых данных: это может нарушить защиту от повторных наград. Изменения баланса исправлять отдельной согласованной миграцией.
