# v0.10.0 — публикация, миграция и откат

Глава I «Лес, который забыл нас». Ветка `claude/chapter-1-v0.10.0`, основание — `origin/main` `fa6fafc` (v0.9.3 + медальоны + акварельный колдун).
Бэкап предыдущей рабочей версии: ветка **`backup/v0.9.3-art-before-v0.10.0`** → `fa6fafc` (текущая `main` перед главой). Более ранний бэкап `backup/v0.9.3-before-v0.10.0` → `98fe04b` сохранён как был.

**Публиковать только после приёмки владельцем.** Порядок важен: сначала SQL, потом клиент.

## 1. Резервная копия облачных сохранений (Supabase → SQL Editor)

Git-ветка не откатывает сохранения игроков. Перед миграцией выполнить (один раз, имя с датой):

```sql
create table if not exists backup_v093_player_progress  as select * from public.player_progress;
create table if not exists backup_v093_player_inventory as select * from public.player_inventory;
create table if not exists backup_v093_player_abilities as select * from public.player_abilities;
create table if not exists backup_v093_player_quests    as select * from public.player_quests;
create table if not exists backup_v093_player_world     as select * from public.player_world;
create table if not exists backup_v093_profiles         as select * from public.profiles;
create table if not exists backup_v093_game_hero_levels as select * from public.game_hero_levels;
-- проверка: числа строк совпадают
select (select count(*) from public.player_progress) live, (select count(*) from backup_v093_player_progress) backup;
```

Таблицы-копии без RLS-доступа для `anon/authenticated` (создаются владельцем, клиентам не видны).

## 2. Миграция сервера

Supabase → SQL Editor → вставить **весь** `supabase/schema.sql` из этой ветки → Run. Файл, как и раньше, повторяемый (идемпотентный). Что меняется:

1. `game_hero_levels` — уровни 6–10 (650/940/1300/1750/2350 XP; max HP 152…190; max мана 125…155). Иначе сервер обрезал бы новый запас маны и считал неверный уровень.
2. `player_progress.recent_actions jsonb` (новая колонка, по умолчанию `[]`) — сохранённые результаты последних 20 атомарных действий: повтор того же запроса возвращает тот же результат без нового списания.
3. `_game_rules()` — рецепты, применения сюжетных предметов, награда первого крафта и правило миграции (генерируется `node tools/sql/gen-rules.mjs` из `src/config/storyItems.js` + `recipes.js`; совпадение проверяет `tools/sql/diff-test.mjs`).
4. `player_action` — новые операции `craft`, `use`, `migrate_v10` (прежние `heal`, `starter_kit` без изменений).

Проверка после Run:

```sql
select level, xp, max_hp, max_mana from public.game_hero_levels order by level;          -- 10 строк
select column_name from information_schema.columns where table_name = 'player_progress' and column_name = 'recent_actions';
select jsonb_object_keys(public._game_rules() -> 'recipes');                              -- 6 рецептов
```

Совместимость: **старый клиент v0.9.3 работает с новой схемой** (лишняя колонка ему не мешает, прежние операции на месте, уровень 6+ он покажет как последний известный). Поэтому SQL можно выполнить заранее, до публикации клиента.

### Миграция сохранений

Отдельный SQL-скрипт по сохранениям не нужен: каждый игрок мигрирует при первом входе новой версии одной операцией `player_action { op: 'migrate_v10' }` с флагом `mig_v10`:

| Старое состояние | После обновления |
| --- | --- |
| До алтаря, огоньки в сумке | Огоньки сохранены; цель «Сварите Лунный фитиль» |
| `lunar_quest_complete` есть | Алтарь и награды завершены; фитиль не нужен |
| ТК II запущен / завершён | Таймер и оплата сохранены; цены повторно нет |
| Огонь, корни сожжены | Путь открыт; Корневики и тайники доступны |
| Страж побеждён | Проход и награда сохранены; цель — состав и знаки |
| Страж побеждён, ядра нет, связку не делали | **Одно** ядро (флаг `mig_v10` ставится всегда — повтор и перезагрузка ничего не выдают) |
| `seal_required_01` / `prototype_complete` | Считаются прежним финалом прототипа, **не** `chapter_1_complete` |
| Поражение у врага | Позиция, мана и «Сразиться снова» сохранены |
| Героиня стояла в новой стене у ворот / за закрытыми воротами | Ставится перед воротами (900, 540), не к дому |
| Ведьма / колдун | Выбор, ник и прогресс не меняются |

## 3. Публикация клиента

1. Влить PR в `main` (GitHub → Merge). GitHub Actions соберёт и выложит Pages автоматически.
2. Открыть игру, войти тестовым аккаунтом (не сбрасывать реальные): в меню «v0.10.0 · Глава I».
3. Быстрая проверка: котёл показывает 6 рецептов; журнал показывает цель; у старого аккаунта со Стражем — ядро в сумке ровно одно.

## 4. Откат

**Клиент.** Откатить `main` к последнему коммиту до слияния (обычно `fa6fafc`):

```bash
git checkout main && git pull
git revert -m 1 <merge-коммит PR>      # или: git reset --hard fa6fafc && git push --force-with-lease (только владелец)
git push
```

Pages пересоберётся сам. Сохранения, сделанные v0.10 (новые события, предметы `lunar_wick`, `revealing_compound`, `restoration_bundle`, уровни 6–10), старый клиент читает без падений: незнакомые предметы показываются строкой в сумке, события игнорируются.

**Сервер** откатывать обычно не нужно (см. совместимость). Если всё же нужно вернуть функции v0.9.3 — выполнить `supabase/schema.sql` из ветки `backup/v0.9.3-art-before-v0.10.0` (колонка `recent_actions` и уровни 6–10 останутся и не мешают).

**Сохранения** (только при порче данных, по одному игроку или всем):

```sql
-- один игрок
begin;
delete from public.player_progress  where user_id = '<uuid>'; insert into public.player_progress  select * from backup_v093_player_progress  where user_id = '<uuid>';
delete from public.player_inventory where user_id = '<uuid>'; insert into public.player_inventory select * from backup_v093_player_inventory where user_id = '<uuid>';
delete from public.player_abilities where user_id = '<uuid>'; insert into public.player_abilities select * from backup_v093_player_abilities where user_id = '<uuid>';
delete from public.player_quests    where user_id = '<uuid>'; insert into public.player_quests    select * from backup_v093_player_quests    where user_id = '<uuid>';
delete from public.player_world     where user_id = '<uuid>'; insert into public.player_world     select * from backup_v093_player_world     where user_id = '<uuid>';
commit;
```

Если новая колонка мешает восстановлению `select *` (у копии её нет) — перечислить колонки копии явно или сначала `alter table backup_v093_player_progress add column recent_actions jsonb not null default '[]';`.

Расхождения с планом и причины (числа баланса не менялись):
- **XP +15 / монеты +95**: существующие необязательные сундуки и находки (поляна 20 монет под камнем, тайники, западный сундук 40 монет + 15 XP) — ТЗ §7 велит их сохранить и отразить в отчёте.
- **Смола и грибы с запасом** (10 / 4): пять Корневиков дают по смоле, сундук Мирры и тайники — грибы; дефицита на пути к связке нет.
- **Пыль впритык** (минимум 0, в конце 1): пыль — самый тесный ресурс главы, как и в модели ТЗ (2 в конце). Новые источники (+1 тайник охранника, +2 запас, +2 тайник на подходе) закрывают фитиль, Эликсир, Склянку и ТК II до этапа C.
- **Ожидание маны** перед сильными боями (бот ждёт 90 % маны) — 4–15 мин сверх плана. Это следствие регена мира +0,5/с; дома — +2/с. При игре «как пойдёт» ожидания нет, но бои идут с меньшим запасом и чаще с эликсиром.
- **Страж узла** — 100 с при подготовке (2 настоя + 2 эликсира, лимит 4 расходника), в целевом окне ТЗ 75–120 с. Без зелий бот проигрывает примерно на 260 HP Стража (`npm test`, раздел «Страж узла»): к испытанию нужно готовиться, но количество зелий не проверяется.
- Без Печати третья фаза заметно опаснее (бот без Печати теряет вдвое больше HP).

Боевые симуляции на текущем движке (`node tests/run-tests.js`): первый Падальщик 27 с; молодой 16 с; Корневик 10–16 с (слабость к Огню); Страж ворот 45–70 с; Страж узла 81–100 с подготовленным. Сценарии «пропуск каждого 2-го/3-го сильного удара» и «старт с половиной маны» ботом не измерялись — бот реагирует мгновенно; это пункт для пользовательского теста.

**Пользовательский тест 5–10 прохождений не проводился** — пункт остаётся открытым.

## 6. Что проверено и ограничения

- `npm test` — логика, мир (проходимость, ворота-преграда, испытание стережёт узел), объекты главы, фазы, старые сохранения; `npm run test:db` на Postgres 16 — настоящие SQL-функции: рецепты и применения совпадают с JS-зеркалом, повтор / потерянный ответ / новый ID не дублируют, миграция ядра один раз.
- `npm run e2e` — бот проходит всю главу в Chromium (ведьма и колдун); `test:mobile` — на **390×844** (по договорённости — один размер; 360×800 и 412×915 не прогонялись).
- `npm run build` (Vite) локально недоступен — сборку делает GitHub Actions; локально — esbuild тем же исходником.
- Физический телефон не проверялся; production Supabase не обновлялся.
- Сервер не авторитетен для боёв (награды побед, в том числе повторных Корневиков, — обычным сохранением, как в v0.9); атомарны крафт, применение сюжетных предметов, лечение, стартовый набор и миграция.
