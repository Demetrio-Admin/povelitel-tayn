# Игровой чат

Чат подключён к пункту игрового меню, к существующей сессии Supabase и к серверному прогрессу v0.10.0. В браузере нет демонстрационных пользователей или локальных «банов». Если миграция не установлена, игрок видит сообщение о недоступности, повтор подключения и кнопку закрытия.

## Включение на сервере

1. В SQL Editor Supabase выполнить актуальный `supabase/schema.sql`, затем **целиком** `supabase/migrations/20261004_game_chat.sql` и `supabase/migrations/20261004_chat_roles_v2.sql`. Все три файла можно применять повторно. Существующие персонажи, инвентарь, никнеймы и прогресс сохраняются.
2. После установки базы опубликовать клиент этой ветки, войти своим аккаунтом и посмотреть собственный числовой ID в профиле. Владелец назначается **один раз через доверенный SQL Editor**, а не из браузера и не по никнейму:

```sql
-- Заменить 123 своим ID. SELECT ниже позволяет проверить выбранный профиль до назначения.
select player_id, nickname from public.profiles where player_id = 123;
insert into game_chat.roles(user_id, roles)
select id, array['owner']::text[] from public.profiles where player_id = 123
on conflict(user_id) do update set roles = excluded.roles, revision = game_chat.roles.revision + 1;
```

3. В уже работающем чате достаточно выполнить новую миграцию `20261004_chat_roles_v2.sql` целиком, затем публиковать клиент. Она сохраняет обращения, прогресс и постоянные ID. Старые совмещённые роли заменяются старшей ролью: владелец → администратор → разработчик → поддержка → модератор.
4. Владелец назначает и снимает администраторов прямо в игре. Администратор назначает модератора, поддержку и разработчика. Путь: «Чат → Роли по ID → Найти → Новая роль → Причина → Было / станет → Подтвердить». Выбирается одна роль; «Игрок» снимает служебную роль. Назначение владельца остаётся доверенной операцией SQL.
5. Существующих публичных переменных `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY` достаточно; дополнительные ключи в браузер не нужны. Числовой ID собственного аккаунта доступен и до назначения служебной роли.

До установки новой миграции клиент сохраняет работу чата и обращений со старым сервером: новые служебные операции скрыты, администрация видит сообщение, что новые функции ролей ещё не включены. После установки клиент узнаёт версию политики из серверного профиля и включает новые права при следующем опросе, без перезагрузки страницы.

Миграция устанавливает проверки игровой блокировки на `get_player`, `create_player`, `reset_player`, `sync_player`, `player_action`, включая уже выданные токены. Повторная установка основной схемы сохраняет эти проверки. Обжалование и поддержка доступны заблокированному аккаунту из стартового меню.

## Что доступно

Снимки интерфейса из браузерного прогона с тестовыми аккаунтами:

![Мобильный чат](images/game-chat-mobile.png)

![Ответ поддержки на большом экране](images/game-chat-support.png)

| Роль | Возможности |
|---|---|
| Игрок | Общий чат, помощь, чтение новостей, личные сообщения, ответы, профиль, игнор, жалобы и свои обращения. Свои сообщения редактировать и удалять нельзя |
| Модератор | Права игрока; жалобы и журнал, удаление публичных сообщений с причиной, восстановление собственных удалений в течение 24 часов; предупреждения и муты до 30 дней, отмена собственных ограничений |
| Техподдержка | Все права модератора; очередь, назначенные обращения, ответы, заметки, создание/редактирование/архивирование общих шаблонов, технические задачи и передача администратору; игровые баны и муты вплоть до бессрочных, отмена собственных ограничений |
| Разработчик | Все права поддержки; новости, назначенные технические задачи; выдача/изъятие предметов и ресурсов, смена никнейма по ID |
| Администратор | Все права разработчика; снятие ограничений нижестоящих ролей, закрепления; назначение модераторов, поддержки и разработчиков по ID; распределение обращений |
| Владелец | Все административные права; назначение и снятие администраторов в игре. Защищён от наказаний и изменения роли |

Одна роль на аккаунт. Полномочия наследуются по порядку: игрок → модератор → поддержка → разработчик → администратор → владелец. Сотрудник может наказывать и изменять только нижестоящих; равные роли и вышестоящие защищены. Модератор не наказывает сотрудников, администратор не наказывает другого администратора или владельца. Наказывать себя и назначать себе роль нельзя. Сотрудник может удалить собственное публичное сообщение с причиной и исправить свой текст в первые три минуты; приватная переписка не модерируется через эти кнопки.

Числовые ID видят **все роли**, в сообщениях и доступных профилях. ID постоянный: регистрация гостя, сброс прогресса и переименование его не меняют. ID не открывает приватную переписку или UUID входа. Цвет надписи роли, никнейма и текста совпадает; у владельца отдельный светлый бирюзовый цвет `#99e6d3`.

Все экраны чата, профилей, модерации, подтверждений, ролей и поддержки совпадают с границами игрового canvas. На компьютере чат сохраняет вертикальные пропорции игры и боковые поля; размеры обновляются при изменении окна и масштаба Phaser. При открытии экранной клавиатуры окно чата занимает видимую часть игры. Адаптивная раскладка зависит от размеров самого чата, а не всего браузера. «Назад» возвращает предыдущий экран, крестик закрывает чат. Игра на паузе; клавиатура и джойстик не управляют героем во время ввода. Вступление в бой закрывает чат. Шрифты с кириллицей и SVG-иконки загружаются из самой сборки.

Сообщение: до 500 символов Unicode, до трёх упоминаний, не чаще одного за три секунды / двадцати за минуту. У обычного игрока нет самостоятельного редактирования или удаления. HTML отображается обычным текстом. Удаления оставляют пустую отметку, обновляют цитаты и доходят на другое устройство. История загружается по 50 сообщений, в ленте не больше 150; старые страницы доступны отдельной кнопкой. Игнор скрывает обычные сообщения и блокирует личную переписку; официальных сотрудников игнорировать нельзя.

## Работа поддержки

- Игрок создаёт обращение: аккаунт, ошибка игры, вопрос, обжалование. Тема до 100 символов, описание / ответ до 2000. Одно незакрытое обращение в категории, до трёх новых за сутки; отдельное обжалование доступно даже при исчерпании обычного лимита. Повтор сообщения игроком — не чаще 10 секунд / 20 за час.
- Сотрудник видит очередь и атомарно берёт свободное обращение. Второй сотрудник не может перехватить его старым запросом. Администратор может назначить сотрудника из списка поддержки, разработчиков и администрации. Очередь показывает метаданные; полная переписка открывается автору и назначенному сотруднику.
- «Ответ игроку» и «Внутренняя заметка» — разные поля, черновики и серверные таблицы. В пользовательском ответе RPC нет заметок. Шаблоны хранятся на сервере и общие для команды. Роль поддержки и выше создаёт, изменяет и архивирует их через «Поддержка → Шаблоны». Выбор шаблона вставляет редактируемый текст, отправка остаётся отдельной кнопкой.
- Публичный ответ переводит обращение в «Ждём игрока», ответ игрока — в «В работе». «Ответить и решить» записывает непустой публичный ответ и статус одной транзакцией.
- Игрок выбирает «Всё решено» или «Проблема осталась». Закрытое обращение можно вернуть в работу в течение семи дней. История остаётся доступной.
- Разработчик получает только проверенное сотрудником техническое описание. Его ответ виден поддержке; она передаёт решение игроку. Техническая задача не содержит всего обращения или заметок. Разработчик также может отдельно взять свободное обращение как сотрудник поддержки: полную переписку он видит только при назначении на это обращение.
- Сотрудник не завершает обжалование санкции, выданной им самим. Модератор, поддержка и разработчик снимают собственные ограничения; администрация снимает ограничения нижестоящих ролей.

Сотрудник поддержки или разработчик может передать своё обращение администратору с внутренней причиной. Оно становится свободным в отдельной очереди администрации. Взять его может администратор или владелец; прежний исполнитель сразу теряет доступ к переписке. Администрация может взять обращение или назначить другого сотрудника. Причина передачи не попадает в ответ игроку.

## Ресурсы и переименование

«Чат → Игрок по ID» доступен разработчику, администратору и владельцу. Карточка показывает найденный никнейм, ID, уровень и текущее количество выбранного ресурса. Сотрудник выбирает предмет, выдачу/изъятие, целое количество и обязательную причину. Подтверждение показывает количество до/после. Сервер проверяет ревизию, каталог игры, наличие ресурсов и защищённость аккаунта; повтор потерянного ответа не выдаёт награду дважды. Дельтовое сохранение игрока не перезаписывает выдачу. Изменение доходит на активный клиент при следующем опросе чата через обычную синхронизацию прогресса.

Переименование сохраняет ID, прогресс и пароль. Форма входа принимает **только текущий новый никнейм**: старый отклоняется до запроса Auth. `nickname_login` разрешает текущий ник в неизменную служебную идентичность Supabase; исходный ник остаётся зарезервированным, чтобы не связывать новый аккаунт с прежним Auth-адресом. В браузере пользователь видит только никнейм, без служебного адреса. Все переименования и изменения ресурсов содержат причину и значения до/после в журнале.

## Безопасность и обмен данными

Единственный RPC чата: `chat_request(op, args, request_id)`. Вход дополнительно использует публичный `nickname_login(norm)`, регистрацию — `nickname_available(norm)`. Auth берётся из действующей `PlayerSession`; свои хранилища токенов чат не создаёт. Таблицы и вспомогательные функции находятся в закрытой схеме `game_chat`, на таблицах включён RLS без клиентских политик. Прямой доступ и стандартное право PUBLIC EXECUTE отозваны. Точка входа использует `SECURITY DEFINER`, пустой `search_path` и квалифицированные имена.

Сервер проверяет роли заново, не доверяет `user_metadata`, нику и роли из аргументов. Все изменения выполняются транзакционно. Блокировки пользователей берутся в одном порядке, затем блокируется комната / обращение. У комнаты собственный счётчик последовательности: он растёт под блокировкой строки и соответствует порядку фиксации сообщений и изменений. Bigint-номера передаются JSON-строками. Изменение ролей / сообщений / обращений / шаблонов / ресурсов / никнейма требует актуальной ревизии; конфликты не затирают чужую работу.

UUID запроса позволяет безопасно повторить отправку после потери ответа. Клиент повторяет тот же UUID; сервер проверяет, что аргументы не подменили. История после разрыва получает изменения, включая отметки удалённых сообщений. Жалоба сохраняет серверный снимок выбранного сообщения и максимум трёх соседних с каждой стороны в той же комнате; модератор не получает доступ ко всей личной переписке.

Для текущего клиента используется опрос RPC раз в пять секунд при открытом чате и раз в тридцать секунд для важных уведомлений при закрытом. Скрытая вкладка не делает запросов истории. В Realtime не передаётся приватный текст; подписки с устаревшими правами отсутствуют. Уведомления: личные сообщения, упоминания, новости, непрочитанные ответы поддержки. Черновики хранятся только в памяти текущего браузерного сеанса и очищаются при выходе / смене аккаунта.

## Хранение и проверки

`chat_cleanup()` доступна только серверу: общий чат 30 дней, личный 90, закрытая поддержка 90 дней после закрытия, прежние редакции 30, журнал 180. Открытые жалобы удерживают исходные сообщения; закрытые ещё 30 дней. Идемпотентные ответы хранятся семь дней. ID-счётчик не сбрасывается.

Включить `pg_cron` в Supabase и добавить ежедневную задачу (один раз):

```sql
select cron.schedule('game-chat-retention', '15 3 * * *', $$select public.chat_cleanup();$$);
```

Проверки:

```sh
npm test
npm run test:chat
npm run test:chat:browser
npm run build
```

`test:chat` использует реальный PostgreSQL-движок PGlite, а не JS-копию правил. `test:chat:browser` запускает Phaser, настоящий интерфейс и те же SQL-функции; только транспорт Auth подменён тестовыми аккаунтами. Можно задать `CHROME_PATH` и `UI_SHOTS_DIR`. Для проверки в данном окружении использован Playwright: Browser plugin недоступен. Это не проверка применённой базы Supabase или опубликованной игры; перед выпуском миграцию необходимо установить на целевой проект. PGlite выполняет тесты последовательно, поэтому отдельный нагрузочный прогон конкурентных клиентов на целевом PostgreSQL остаётся релизной проверкой.
